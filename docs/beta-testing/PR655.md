# PR-655 beta hardware checks

> **Device-test checklist**
> Scope: [what the device test checks](README.md#what-the-device-test-checks).

Physical-device testing is pending. Use these detailed checks when investigating
a device issue or testing additional settings.
See the [beta guide](README.md) for downloads and reporting.

## Device checklist

These checks establish basic operation for the tested model and setup. They do
not establish measurement accuracy. PR-670 support remains partial and tentative.

### 1. Record the setup

Record the model, MATLAB release, operating system, USB or RS-232 connection,
fitted optics and physical setup. Include the tested Git revision or ZIP download
link/date. Record useful identity/setup information from the instrument display
or labels. The window selects adaptive exposure, one cycle and automatic
synchronization before each reading, with optional overrides under **Settings...**.
Direct commands and core sessions using `colormeasure.drivers.pr.adapter()` preserve existing
settings. Retain the settings receipt when comparing these workflows and match
the actual acquisition settings. Additional post-measurement metadata queries remain disabled; the
[optional metadata check](#optional-metadata-check) tests those reports separately
after the basic acquisition and saving checks.

Use a steady target, keep its geometry and illumination fixed, and follow the
[instrument setup instructions](../drivers/pr/README.md#acquisition-settings).
A steady setup does not establish that the source is free of temporal modulation;
test synchronization separately as described below.

### 2. Open a batch

With the repository **src** folder on the MATLAB path, open the measurement window:

```matlab
session = colormeasure.drivers.pr.measurePR655();
if isempty(session), return; end
```

Choose a save folder. Confirm that opening the window has not acquired a reading.
A single available
candidate is selected automatically; model verification happens when connecting.
Multiple candidates require selecting the meter's port. Do not guess among
unrelated devices; use [port diagnostics](../drivers/pr/README.md#port-diagnostics).

The launcher restores an existing batch if one is already open. These checks
need a fresh, empty batch. If a previous batch was restored, finish it when ready
and create the test batch explicitly:

```matlab
session.finish();
session = session.newBatch();
if isempty(session), return; end
```

Continue only with an empty, unfinished session:

```matlab
assert(isempty(session.measurements) && ~session.finishing);
```

Open **Settings...**, then select **Read settings**. Compare the reported setup
with the meter display. Confirm the batch still has no readings and that the
port is released. Inspect the help for Exposure, Cycles, and Synchronization;
leave overrides clear for the first repeat set.

### 3. Acquire three readings

Enter a sample name and notes, position the target, then select **Measure** once.
The equivalent Command Window action is shown below; use either the button or
the command for each reading:

```matlab
session.measure('Sample 001', 'Stable target, first reading');
```

- Confirm exactly one reading appears in `session.measurements`.
- Check its `deviceType` matches the connected instrument.
- Inspect `instrumentSettings`: the requested automatic recipe should be
  adaptive exposure, one cycle and automatic sync. Retain before/after reports
  and any unsupported or unknown values; an acknowledgement alone is not
  independent verification.
- Confirm optional `instrumentMetadata.queries` records are `notQueried` in
  this default workflow. Empty identity/settings fields do not invalidate the
  completed spectrum; do not fill them with assumed values.
- Check `lambda`: PR-655 has 101 values from 380 to 780 nm at 4 nm intervals;
  PR-670 has 201 values at 2 nm intervals. `radiance` has the same length.
- Confirm `session.savedCount` is 1 and `session.files.mat` exists.

Wait before each next reading. Nothing should measure while adjusting the setup.
Keep the same stable target for these repeats and execute each command separately:

```matlab
session.measure('Sample 002', 'Stable target, second reading');
```

```matlab
session.measure('Sample 003', 'Stable target, third reading');
```

Confirm the count advances once per command, all three spectra and notes remain
in the struct array, and the same batch MAT is updated. Inspect repeat differences
without assigning an arbitrary accuracy tolerance.

### 4. Finish and verify the saved batch

Select **Finish batch**, or use `session.finish()` as below.

```matlab
session.finish();
assert(session.finished);
assert(isfile(session.files.mat) && isfile(session.files.csv));
saved = load(session.files.mat);
assert(isequaln(saved.measurements, session.measurements));
assert(saved.batchInfo.acquisitionComplete);
assert(session.savedCount == numel(session.measurements));
csv = readtable(session.files.csv);
assert(height(csv) == sum(arrayfun(@(m) numel(m.lambda), session.measurements)));
session.files
```

The MAT must contain every acquired spectrum. The CSV has one row per wavelength,
with `MeasurementIndex` identifying each reading. Prepare another batch:

```matlab
nextSession = session.newBatch(); % Equivalent to New batch; retains its handle
if isempty(nextSession), return; end
nextSession.selectPort(session.port);
```

Position the target before running its single reading:

```matlab
assert(nextSession.measure('Sample 001', 'Second batch check'));
nextSession.finish();
assert(nextSession.finished);
assert(~strcmp(nextSession.files.folder, session.files.folder));
assert(isequaln(load(session.files.mat,'measurements'), ...
    struct('measurements',session.measurements)));
```

### 5. Report the result

Return the software report folder, batch MAT/CSV, setup details, and which steps
passed. For a problem, include the exact error, the action immediately before it,
and the separately saved [session log](../session/README.md#diagnostics-and-provenance).

## Window checks

Before finishing a batch, close the window and rerun `colormeasure.drivers.pr.measurePR655`. Confirm the
same unfinished batch reopens without acquiring another reading. Check that the
selected table row and both plots refer to the same sample, and that long notes
can be inspected and copied.

For a larger synthetic collection, run `colormeasure.drivers.pr.demoPR655('gallery')`. Inspect the table,
spectra and xy/u′v′ plots; scroll to older readings and return to the latest one.
In the log, select an older entry, verify the surrounding history remains, then
use **Jump to latest**. See the [window guide](../ui/README.md).
Synthetic data can exercise controls but cannot validate the meter.

The [derived-view checks](UI.md#window-checks-without-hardware)
cover white adaptation, reference-based object color, source preservation and
separate analysis export. Repeat those checks for the intended device demo.

## PR-655 instrument comparison

Use the same connected PR-655, target, geometry, optics and exposure/sync settings.
Keep the source stable. Take three original readings, three current readings, then
three original readings again to help distinguish a version difference from drift.
For Adaptive exposure, leave the setting unchanged; exposure can vary between
individual acquisitions. Compare the default acquisition path first. The
optional metadata check below can separately retain reported exposure.

The folders and class names make the choice explicit.
Never keep two connections to the same meter open. Finish any active UI batch
before beginning this direct-driver comparison. Keep the target in position when
changing versions.

Use a separate school checkout for the original driver. With this repository's
**src** folder already on the MATLAB path, prepare once:

```matlab
schoolRoot = '/path/to/MCSL-Tools';
addpath(fullfile(schoolRoot,'Devices','PR655'), fullfile(schoolRoot,'Convert'));
which PR655          % Original: school checkout / Devices/PR655/PR655.m
which colormeasure.drivers.pr.PR655 % Current: src/+colormeasure/+drivers/+pr/PR655.m
portName = 'COM3';   % Replace with the connected meter's port
% portName = '/dev/cu.usbmodem101'; % macOS example
folder = uigetdir(pwd, 'Save original-current comparison');
if isequal(folder,0), return; end
comparisonFolder = tempname(folder); mkdir(comparisonFolder);
```

For each round, run its connection block, then the **acquire and save** blocks
below. Complete and release one round before opening the next:

```matlab
% Round 1: original
resultFile = fullfile(comparisonFolder, 'original_before.mat');
assert(~isfile(resultFile), 'This round has already been saved.');
pr = PR655(portName);
```

```matlab
% Round 2: current, after saving and releasing round 1
resultFile = fullfile(comparisonFolder, 'current.mat');
assert(~isfile(resultFile), 'This round has already been saved.');
pr = colormeasure.drivers.pr.PR655(portName);
```

```matlab
% Round 3: original again, after saving and releasing round 2
resultFile = fullfile(comparisonFolder, 'original_after.mat');
assert(~isfile(resultFile), 'This round has already been saved.');
pr = PR655(portName);
```

**Acquire:** run this command once when ready. Repeat it separately until the
round contains three readings; it does not start the next reading automatically.
The original method has no return value.

```matlab
pr.measure();
```

**Save and release:** after the three readings, save ordinary arrays, then close
the connection. This shared schema works for both versions:

```matlab
result = struct('lambda',pr.wl, 'radiance',pr.radiance, ...
    'XYZ',pr.XYZ, 'totalRadiance',pr.totalRadiance);
if isprop(pr, 'instrumentMetadata')
    result.instrumentMetadata = pr.instrumentMetadata;
end
assert(size(result.radiance,2) == 3, 'Collect three readings in this round.');
assert(~isfile(resultFile), 'Choose a new file instead of replacing this round.');
save(resultFile, 'result');
delete(pr); clear pr
```

If an original acquisition stops responding, use Ctrl+C and release the connection
with `delete(pr)` before switching. The original driver has unbounded waits;
record the failure rather than trying to obtain a numerical match from an
incomplete reading. Save any successful original arrays before releasing them.
For other failures, retain the exact message and current arrays as well.

After all rounds, compare the common fields:

```matlab
a = load(fullfile(comparisonFolder,'original_before.mat'), 'result');
b = load(fullfile(comparisonFolder,'current.mat'), 'result');
c = load(fullfile(comparisonFolder,'original_after.mat'), 'result');
assert(isequal(a.result.lambda,b.result.lambda,c.result.lambda));
means = [mean(a.result.radiance,2), mean(b.result.radiance,2), ...
    mean(c.result.radiance,2)];
plot(a.result.lambda, means);
xlabel('Wavelength (nm)'); ylabel('Spectral reading (instrument units)');
legend('Original before','current','Original after');
deltaXYZ = mean(b.result.XYZ,1) - mean(a.result.XYZ,1);
spectralRMS = sqrt(mean((means(:,2) - means(:,1)).^2));
repeatSpread = [std(a.result.radiance,0,2), std(b.result.radiance,0,2), ...
    std(c.result.radiance,0,2)];
```

Identical replay bytes should agree numerically. Separate physical readings need
not be bitwise equal: inspect differences alongside variation within each round
and movement between the two original rounds. Spectral RMS is a raw spectral
quantity in the same units, not a perceptual difference or accuracy score. Three
repeats are a practical check, not an uncertainty budget or a significance test.
There is no universal pass percentage here. Report an unexplained systematic
difference with all three files and the setup; do not dismiss it as expected noise.

This original-versus-current baseline is for PR-655. PR-670 uses 201 samples at 2 nm;
its current support remains partial and tentative. The school has no PR-670 for
physical validation.

## Synchronization check

When testing the automatic recipe, take a reading of a stable display and, if
available, a source known to operate without periodic modulation. Keep geometry
fixed within each condition. Record the source, synchronization mode and settings
receipt; a display or lamp type alone does not establish its modulation.

If `-3`, `-9` or `-10` occurs, retain the full error and confirm that no reading
was appended. Follow [synchronization errors](../drivers/pr/settings.md#synchronization-errors)
to inspect the signal and select an appropriate mode. For a known nonmodulated
source or a labelled diagnostic repeat, explicitly apply `syncMode='none'`, check
the receipt, then confirm the target before measuring again. Record this as a
changed condition. Do not disable sync automatically or infer measurement
accuracy from a successful repeat. Record an unavailable source type as untested.

Before starting another window reading, retain the failed attempt's receipt and
log; the next reading replaces `session.lastSettingsReceipt`:

```matlab
failedSettingsReceipt = session.lastSettingsReceipt;
failedLog = session.log;
```

In the window, open **Settings...**, select **Synchronization**, enable
**Override this setting**, choose **None**, and select **Use for next readings**.
Confirm the target, then select **Measure**; staging the override does not take a
reading. Retain the new receipt separately. To return to Automatic, uncheck
**Override this setting** for **Synchronization**, then select **Use for next readings**.

## Optional metadata check

Run this after the default workflow succeeds. Finish any active session and
release its connection. Use the port from that session and choose where to keep
the separate report; no other program should own the meter.

Connect with the extra reports enabled. This does not start a measurement:

```matlab
portName = session.port;
metadataFolder = uigetdir(pwd, 'Save optional metadata check');
if isequal(metadataFolder,0), return; end
pr = colormeasure.drivers.pr.PR655(portName, 'Metadata', true);
```

Position the target, then run this block once. It requests one spectrum followed
by the enabled reports, records elapsed time, and releases the connection:

```matlab
try
    started = tic;
    metadataReading = pr.measure();
    metadataElapsedSeconds = toc(started);
catch err
    delete(pr);
    rethrow(err);
end
delete(pr);
metadataReading.instrumentMetadata
metadataReport = [tempname(metadataFolder) '.mat'];
save(metadataReport, 'metadataReading', 'metadataElapsedSeconds');
```

Inspect all five records under `instrumentMetadata.queries`: `D110`, `D114`,
`D602`, `D13`, and `D14`. Compare available serial/version/settings values with
the instrument display, and report elapsed time, raw replies and each status.
A returned spectrum alone does not confirm metadata support. `unsupported`,
`error` or skipped `notQueried` records must be reported as such. The first
uncertain reply stops the remaining queries; the completed spectrum is retained.
Current setup is not an atomic record of the settings at exposure time.

Repeat with the same stable target if checking latency consistency. Each block
is manually triggered. Keep these opt-in results separate from the default
original/current/original comparison. Metadata remains disabled by default until its
post-measurement behavior has been validated on the intended instrument/firmware.

## Optional checks

- Close the batch normally, reconnect, and verify another reading succeeds.
- Check a missing/unavailable port **before** acquisition, then correct the port
  and retry. Prior readings should remain intact.
- If instrument-screen results are available, compare them with software values
  under the same stable setup and record discrepancies. First confirm quantity,
  units and calculation conventions; see [spectral data and units](../drivers/pr/api.md#spectral-data-and-units).
  Do not assume every Y value is cd/m² or treat a difference as a calibration failure.

Routine testing does not require unplugging during acquisition or forcing storage
failures; those error paths are covered by simulated software tests.


## Serial write deadline qualification

Use R2026b or newer for native connections. Software tests simulate blocked
and partial writes and verify that earlier readings survive without automatic
retries. They do not establish operating-system or physical-link behavior.
During an authorized bench session, record normal writes on the actual USB or
RS-232C path and confirm the configured write deadline. Only use an approved
isolated loopback or flow-control fixture to test blocked writes; do not cause
a partial command or unplug the instrument during acquisition. A failed write
requires checking that the instrument is idle before reconnecting, including
its remote/backlight state where applicable.
