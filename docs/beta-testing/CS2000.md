# CS-2000 device-validation checklist

> **TEMPORARY BETA VALIDATION GUIDE**
> Scope: [validation status and interpretation](README.md#validation-status-and-interpretation).

Physical-device validation of the current release is pending. Use this checklist
to record which model, firmware, operating system and transport have been tested.
Keep passing, failing and untested cases distinct; software simulations do not
establish optical or physical-device behavior.

Start with the [beta testing guide](README.md) for the testing download,
software command and demonstration without an instrument. Routine operation is
covered by the [CS-2000 measurement guide](../drivers/cs2000/README.md).

## Instrument checklist

This checklist is for a lab session and is **not executed by `colormeasure.runTests`**.
Use the current [measurement guide](../drivers/cs2000/README.md) and
[protocol/data reference](../drivers/cs2000/protocol-and-data.md), plus the
[metadata reference](../drivers/cs2000/metadata.md), for commands and expected
metadata. Do not use equipment occupied by another measurement session.

1. **Prepare.** Run the software command first and retain its revision/platform
   report. Record model, connection type and the operator's intended speed,
   observer, measurement angle and target. The saved metadata should retain
   device-reported serial/identity automatically; inspect those fields after
   saving. Record the firmware shown on the startup display following the
   [metadata guide](../drivers/cs2000/metadata.md#firmware-temperature-and-sdk-limits);
   the communication identity intentionally leaves firmware empty.
   Follow the [preparation guide](../drivers/cs2000/preparation.md): record power-on/warm-up
   completion in the experiment notes. Use the intended calibration channel;
   ordinary measurement does not require creating a calibration.
   Apply the operating manual's minimum 20-minute warm-up and aperture-specific
   low-luminance thresholds, including after a power cycle. A host connection
   timestamp does not establish thermal readiness. Verify any selected user
   correction is intentional; do not create a user calibration or send `INIT`
   merely to begin a measurement.
2. **Connect without measuring.** Construct `colormeasure.drivers.cs2000.CS2000()` and confirm construction
   does not enumerate/open a port. `Connect()` selects and verifies a candidate
   but enters remote mode, disables the physical measurement key and manages
   backlight settings. Inspect identity and its factory-calibration snapshot, then
   `Disconnect()`. Repeat with an explicit port and verify release/restoration.
   Check macOS `tty`/`cu` alias handling where applicable. Keep wrong-model,
   absent/multiple-port and busy-port cases simulated unless the operator can
   arrange them without contacting unrelated equipment.
3. **Check physical RS-232C separately.** Match the instrument's configured
   baud and hardware flow control. In particular, exercise the documented
   `BaudRate=9600` configuration when available; USB defaults of 115200 and no
   flow control are not proof of RS-232C behavior. Record the OS and actual
   transport used. Do not change cabling during a measurement.
4. **Measure and reload.** On a stable target, run `colormeasure.drivers.cs2000.measureToFile`, reload
   the saved MAT without connecting and check 401 samples at 380:1:780 nm,
   XYZ and one matching metadata record. Compare instrument-returned XYZ and
   spectral values with the display or vendor application in a separate
   connection. Verify the reported luminance unit before applying a cd/m² or
   fL label; MATLAB does not normalize, clip or resample the measurement.
5. **Check metadata against the device.** Compare available identity, calibration
   date, aperture/measurement angle, integration/exposure, sync, speed and
   observer readbacks with the supported device controls. Verify CS-2000A
   returns the newer speed reply containing its ND selection; legacy short
   replies are accepted only for CS-2000, whose firmware this driver does not retrieve.
   Distinguish current
   connection settings from conditions belonging to the captured reading.
   Verify supported replies survive Save/Load. An ER05 calibration-name reply
   must retain explicit unavailable status. Fully framed but malformed optional
   metadata should retain `unparsed`, raw response and diagnostic without
   losing the completed spectrum/XYZ; other documented nonbusy UCPR failures
   should retain `unavailable`. Do not force unsupported/busy commands on
   equipment to manufacture these cases; the software fixtures cover them.
   Required identity, actual measurement/conditions and manual restoration
   queries must still reject invalid data without partial history. Verify host receipt timestamps
   are not mislabeled as device exposure times. Do not invent a firmware version or temperature when
   no documented command supplies it.
6. **Observe a dark target and the complete cycle.** With an operator-approved dark/low-luminance target,
   record the time before the first `MEAS` response separately from the announced
   acquisition duration. Verify `PreMeasurementTimeout` is at least 35 seconds
   independently of the ordinary response timeout. A documented unmeasurable
   result is a valid outcome for this test; it is not permission to repeat
   exposure automatically. Check that slow pre-measurement does not prematurely
   close an otherwise valid session.
   This tests a weak optical target, not a manual dark calibration. Each ordinary
   instrument reading already includes a light measurement followed by an
   automatic shutter-closed dark measurement of equal integration time
   (operating manual p.78). Keep the target/settings fixed until completion;
   do not insert a lens cap or command a second dark exposure. Compare timing
   and results with the vendor workflow in a separate connection. The announced
   duration already includes the actual cycle; do not double it again.
   Simulated replies cannot demonstrate shutter operation or correct dark
   subtraction. If an actual shutter, cooling or temperature error occurs,
   retain the diagnostic and follow manufacturer troubleshooting; do not induce
   a hardware fault to test it. Confirm no new reading is retained on failure.
7. **Recover from an ordinary measurement error.** Where the target and device
   safely permit a complete `ER10` over-range response, confirm no row is
   appended, prior readings stay intact, the synchronized connection remains
   open and a subsequent explicit `Measure()` succeeds after correcting the
   cause. Do not treat busy/ambiguous errors as equivalent to `ER10`.
8. **Test timeout recovery only under operator control.** Observe or arrange a
   bounded timeout without unplugging an active instrument. Record late-byte
   behavior for the actual OS/driver. Before reconnecting, independently confirm
   measurement has ended and the device is idle. Default reconnect should
   reject pending input; explicit `Connect('DiscardPendingInput',true)` should
   abandon only the old exchange, observe a bounded quiet interval and perform
   fresh identification. Quiet input is not proof that an exposure stopped.
   Confirm no implicit new exposure or setting restoration occurs while the
   stream remains uncertain.
9. **Restore settings and release remote mode.** Check original backlight state
   after normal disconnect and a framed recoverable failure. For
   `MeasureManual()` on a `colormeasure.drivers.cs2000.CS2000manual` object, verify the requested integration setting and
   restoration of the previous speed configuration after success and a safe
   framed failure. Ordinary `Connect` must preserve speed/display observer.
   A separate authorized settings check should start in Manual, explicitly call
   `applyAutomaticSettings`, and verify Multi-Normal/1 s/internal ND Auto/No
   Sync in current readback and appropriate actual exposure conditions. Repeat
   the same recipe and confirm no redundant SPMS/SCMS commands. Verify that
   physical aperture, accessories and correction channel are preserved; only
   test explicit overrides that match the laboratory setup. Check selected
   channel/name, sync-frequency boundaries and the model's supported ND/layout
   combinations. These are persistent changes under RMTS,1: inspect the receipt
   and explicitly restore the laboratory setup afterward. Do not create/delete
   calibration or use an incompatible close-up/external-ND combination.
   Confirm backlight-already-Off sends no BALS, while an actual change is
   restored. Settings operations must not issue MEAS; only a subsequent
   explicit Measure may acquire. Failed receipts must prevent acquisition.
   Inspect `cleanupStatus`; after an uncertain response, the driver may close
   without restoration commands. Confirm remote mode/key lock and settings
   manually before the next session instead of assuming they were restored.
   Rev.7 §1.3.1 documents physical ESC: when idle it cancels Remote Mode;
   during measurement it instead interrupts/cancels that measurement. After
   failed Connect or cleanup, use ESC to release remote mode only after the
   operator has established idle, then confirm settings before reconnecting.
10. **Confirm slot 99 stays unchanged.** If the operator can inspect an existing
    slot 99 value using the manufacturer's controls, record it before and after
    ordinary acquisition without writing a replacement value for the test.
    Acquisition should read the current buffer with `MEDR` and send no `STDS`
    command. Do not erase, overwrite or create stored measurements to demonstrate
    this property. If direct inspection is unavailable, record that part as
    untested; simulated command-order checks remain software evidence only.
11. **Exercise retained history.** Acquire two intentional readings; verify
    spectra, XYZ and metadata have two aligned columns/entries. Erase the last
    reading, erase all and save/reload an empty history. Check a separately
    queried conditions snapshot survives `Erase`. Retry a failed Save using a
    writable filename without acquiring another sample. `Load` must operate
    offline and preserve the saved identity, not attribute old readings to a
    newly connected meter.
12. **Compare original and current only after authorizing the original's effects.**
    Follow the [original–current–original lab procedure](#original-driver-comparison).
    Original acquisition overwrites slot 99 and normalizes speed/observer
    settings. Its undocumented `RMT,1` handshake may fail on the available
    instrument; record that as not tested instead of altering the baseline.
    Compare raw spectra/XYZ under matched conditions, using repeated readings
    to assess variation. No universal tolerance or hardware result is implied
    by the software comparisons.

13. **Check the shared window.** Open **Settings... → Instrument help** before
    acquisition and check the warm-up instructions. Cancel the first-reading
    preparation prompt once; no connection or reading should start. Select
    **Measure** again and accept the preparation prompt. Verify one reading is
    acquired and its raw values, settings receipt and metadata are saved. Check that any
    cleanup warning stays visible in the log, **Finish batch** exports CSV, and
    relaunching restores the same batch. Change serial options only after
    finishing and replacing the session, as described in the
    [batch/UI guide](../drivers/cs2000/batch-and-ui.md).

Record each item as passed, failed or not tested, with artifacts or the exact
observed error. No physical validation is claimed for unsupported strobe
timing, stage movement, mounting or network utilities. An instrument/firmware
or connection type not exercised remains untested.

## Original-driver comparison

This procedure is separate from the software command and has not been
performed. It requires an authorized operator and an unoccupied instrument.
Run the full software command first and keep its report. Do not use these
steps to induce malformed replies or timeouts on equipment; failure cases
remain simulated unless separately authorized.

1. **Authorize and inspect the original's effects.** Original acquisition
   overwrites instrument slot 99 and forces normal speed and observer 0 on
   connection. It also changes backlight settings. Confirm explicitly that
   these effects are acceptable before using the original. If slot 99 must
   be preserved, omit the original acquisition and record the comparison as
   not tested. Use manufacturer procedures for any separately authorized
   backup; do not create or erase stored readings just for this test.
2. **Select each version explicitly.** Check `which CS2000 -all` and
   `which colormeasure.drivers.cs2000.CS2000 -all` against the paths in the
   [measurement guide](../drivers/cs2000/original-comparison.md#selecting-the-driver). Use the
   original API for its run and the qualified current API for its run. Never open
   both connections together. Fully disconnect one version before the next;
   inspect remote mode, key lock and backlight before proceeding.
3. **Hold the physical conditions fixed.** Use the same meter, explicit port,
   geometry, aperture, calibration channel, compensation settings and stable
   target. Record transport/baud and the actual instrument settings. Arrange
   matching normal-speed and observer settings because the original forces
   them. Do not assume the two initializations leave all settings identical.
   Allow appropriate warm-up/stability according to the instrument and target
   instructions. Record the displayed firmware version as described in the
   [metadata guide](../drivers/cs2000/metadata.md#firmware-temperature-and-sdk-limits).
4. **Attempt original–current–original measurements.** Take repeated readings within
   each group, saving separate MAT files. The second original group helps
   reveal drift across the sequence. The old `RMT,1`/`OK` handshake is not in
   verified Rev.7; if it fails, record the actual error and the original
   comparison as not tested. Do not patch the baseline, substitute current's
   handshake or interpret failed initialization as numerical agreement.
5. **Compare raw measurements on the same scale.** Check 401 samples on the
   380:1:780 nm grid and three XYZ values per reading. Check the instrument's
   XYZ/luminance output scale before labeling units. Plot spectra and
   per-wavelength differences, compare XYZ, and inspect within-version
   repeats and drift between the two original groups. Judge cross-version
   differences using observed repeatability, target stability and applicable
   manufacturer specifications. There is no universal tolerance; do not
   normalize, clip or resample to manufacture agreement.
6. **Interpret differences before accepting results.** Metadata fields and
   command histories need not match because current reads the current buffer,
   fixes condition assignments and records additional provenance. For raw
   spectra/XYZ, unexplained differences beyond observed variation require
   checking settings, slot contents, timing and target drift. Manual/strobe
   differences in the table are software regression cases, not a requirement
   to exercise unreliable original variants on hardware.
7. **Retain outcomes and restore the instrument.** Save version/revision,
   relevant settings, MAT files, comparison calculations and each step's
   passed/failed/not-tested outcome. Check the device-reported identity saved
   by current. Verify cleanup and restore the operator's intended state under the
   manufacturer's guidance.
   Mark any untested model, firmware, transport or variant explicitly.

Follow the separate [current laboratory checklist](#instrument-checklist)
for metadata, slot-preservation, slow pre-measurement, cleanup and recovery.
An A/B measurement match does not establish every current failure path, firmware
combination or accessory configuration.

## Serial write deadline qualification

Use R2026b or newer for native connections. Software tests simulate blocked
and partial writes and verify that earlier readings survive without automatic
retries. They do not establish operating-system or physical-link behavior.
During an authorized bench session, record normal writes on the actual USB or
RS-232C path and confirm the configured write deadline. Only use an approved
isolated loopback or flow-control fixture to test blocked writes; do not cause
a partial command or unplug the instrument during acquisition. A failed write
requires checking that the instrument is idle before reconnecting, including
its remote/backlight state where applicable.
