# CS-2000 software tests

## Software checks

With MATLAB's Current Folder at the project root, add `src` and run:

```matlab
addpath(fullfile(pwd, 'src'));
report = colormeasure.runTests;
```

This runs all instrument, session, window and colorimetry tests in a separate
MATLAB process. It blocks physical serial access and retains individual test
results, raw output and Code Analyzer findings. Failed, incomplete, missing or
empty tests fail the run. Existing report folders must be empty. The MATLAB JVM
and a license permitting a second process are required.

```matlab
report = colormeasure.runTests(fullfile(tempdir, 'measurement-checks'));
```

To include original-driver comparisons, supply a separate school checkout:

```matlab
schoolRoot = '/path/to/MCSL-Tools';
report = colormeasure.runTests(tempname, 'SchoolRoot', schoolRoot);
```

Without `SchoolRoot`, only the original-school comparison suites are omitted;
the report identifies that scope. With a supplied baseline, pinned source
identity checks reject missing or changed required files. The runner does not
infer the baseline from the standalone repository's location.

From a terminal at the project root:

```sh
matlab -batch "addpath(fullfile(pwd,'src')); colormeasure.runTests;"
```

Replace `matlab` with its installed executable if necessary. See the
[shared testing guide](workflow.md) for report files, process isolation and
interpretation. A software pass does not establish physical operation,
calibration or Windows behavior. Windows execution remains unvalidated.

## Deadline checks

The deadline checks in `testCS2000Deadlines` run on a simulated clock: the
driver's `Clock` option and the fake port share one
`colormeasuretest.FakeClock`, whose time advances only when the transport's
deadline loop sleeps, so the 35-second pre-measurement policy is exercised
exactly without waiting. For a focused software-only rerun in an otherwise
isolated test process:

```matlab
projectRoot = colormeasure.root();
family = fullfile(projectRoot,'tests','drivers','cs2000');
addpath(fullfile(projectRoot,'tests'));
results = run(testsuite(family));
assertSuccess(results);
```

This selector exercises only simulated transport. Use the full launcher for
retained reports, hardware guards and Code Analyzer output; a focused pass
does not replace the full suite. Do not lower the production timeout merely
to make its deadline test faster.

## Reading and retaining results

| File | Contents |
| --- | --- |
| `matlab.log` | Raw MATLAB output and failure diagnostics |
| `test-results.csv`, `test-results.mat` | Discovered test names, pass/fail/incomplete outcomes and durations; MAT also keeps MATLAB test results |
| `checkcode.txt` | Actual Code Analyzer output, grouped by file |
| `checkcode.json`, `checkcode.mat` | Analyzed filenames and all structured messages |
| `report.json`, `report.mat` | MATLAB/platform, bundle path, exact-repository Git metadata when available, original-comparison scope, timing and totals |
| `hardware-guards/` | Serial API stubs belonging only to the test worker |
| `startup.m`, `finish.m` | Empty hooks that bypass personal startup/shutdown scripts |

Keep a report for the exact checkout tested. A dirty status means the recorded
revision does not describe all source changes. Check named outcomes and raw
Analyzer messages instead of comparing a fixed test count. Tests and analysis
are attempted even when a test fails; process startup failures and interruptions
can leave partial artifacts. Keep generated reports and real measurements
outside the source tree. A copy without its own Git metadata reports that
metadata as unavailable instead of naming an unrelated ancestor repository.
Read `originalComparison` alongside the passing test count.

These checks establish simulated framing, deadlines, error handling, data
integrity, saving and API behavior. They do not establish real OS/driver,
instrument, accessory or firmware compatibility.

## Shared-session adapters and synthetic demonstrations

Direct-driver cases separately verify independent `snapshot()` values,
unchanged saved-state flags, native Save/Load/Erase schema and conditions,
and offline preparation guidance. They require only this family and its
injected transport; the adapter and window suites test their integration.

The one-shot example checks in `testCS2000` cover public connection options,
custom identity selection, response timeout, complete saved results and exactly
one `MEAS,1` per acquisition. Invalid options must fail before commands or saving.
An acquisition failure must release the connection and preserve an existing
output file. Keep these checks aligned with the options documented in the README.

The same full command includes `testCS2000Adapter` and
`testCS2000Presentation`. They do not create UI windows. The adapter tests
execute the actual driver with `colormeasuretest.cs2000.Port` and injected port lists:

- Ordinary defaults and explicit RS-232C options reach the driver; equivalent
  option types/case have equal configuration summaries. Construction stays
  offline and an identity failure releases its owned simulated transport.
- The preparation help is a value-only structure. Reading `session.preparation`
  sends no commands, creates no measurement or save, and changing a returned
  copy cannot change the session's reminder policy. All synthetic modes retain
  the same help while marking the live reminder optional.
- Exactly one `MEAS,1` is sent per reading. The generic `colormeasure.drivers.cs2000.adapter`
  preserves native speed/display-observer settings. The separate
  `colormeasure.drivers.cs2000.uiAdapter` applies its automatic acquisition recipe before reading;
  neither adapter introduces retries, slot-memory commands or a `VERR` query.
- Complete values/raw metadata and the native `snapshot()` survive batch MAT
  saving, native Save/Load and CSV export. Independent conditions ownership
  survives snapshot extraction. CSV uses raw/source/unit fields rather than
  claiming host-computed XYZ.
- An acquisition error appends no session row and releases the port. Failed
  restoration retains a complete reading with `cleanupStatus` and warnings.
- Live unknown-scale XYZ, known-observer chromaticity and fixed-unit spectra
  have separate comparison capabilities. Operator scale-declaration keys
  require consistent identity/geometry/calibration; missing or contradictory
  metadata and claimed unit changes cannot be overridden. Exposure/internal
  ND/display-observer differences do not become false convention mismatches.
- Synthetic profiles cycle over twelve generated shapes without inventing
  instrument replies/identity; their numerical scale is explicit. The headless
  `colormeasure.drivers.cs2000.demoCS2000('batch')` saves two readings and CSV without creating figures.

`testCS2000UISettings` checks UI-only settings hooks, virtual settings that
persist without consuming synthetic readings, rejection of invalid coupled
drafts, retained receipts after MAT saving/reloading, and immutable session
configuration. A native driver with an injected transport verifies applying the
automatic recipe before exactly one `MEAS,1`. Direct-versus-UI hardware
comparisons must match the recipe and overrides and inspect both receipts and
capture metadata; inherited Manual and UI automatic exposure are intentionally
different conditions.

The shared UI suite separately covers rendered controls, session restoration,
interactive/gallery behavior and explicit scale declarations. A headless
family pass does not establish window rendering or physical-device behavior.
The [batch/UI guide](../drivers/cs2000/batch-and-ui.md) explains its controls and saved files.

## Current settings and automatic recipe

The full command also discovers `testCS2000Settings`. It uses the real native
driver with the injected peer to check current readbacks, plain offline help,
automatic acquisition settings from Manual on both CS-2000 firmware layouts,
CS-2000A handling, coupled speed/time/ND and sync/frequency overrides,
unchanged-value skips and channel preflight. It verifies accessory restrictions,
preservation of inherited settings, no exposure/history changes from settings
operations, persistent-change receipts, partial failures, readback mismatches,
quarantine and recovery that requires the complete failed recipe: empty,
unrelated and incomplete applications stay blocked, while complete explicit
reapplication can use either the original or a newly chosen target. Backlight tests cover
skipping redundant writes and retaining restoration after a real change.

For a focused rerun in an isolated, non-desktop MATLAB process:

```matlab
projectRoot = colormeasure.root();
family = fullfile(projectRoot,'tests','drivers','cs2000'); % Current Folder: the project folder containing src
addpath(fullfile(projectRoot,'tests'));
results = runtests(fullfile(family,'testCS2000Settings.m'));
assertSuccess(results);
```

No real port enumeration is needed by these fixtures. The public full command
adds the serial guards, retained reports, Code Analyzer and connected regression
suites. Passing simulated settings tests does not validate hardware, accessory
compensation, physical flash writes or an installed firmware version. The
[settings guide](../drivers/cs2000/settings.md) defines what each receipt proves.

## Compare the actual original implementation with current

With `SchoolRoot` supplied, the command includes [original/current comparisons](../drivers/cs2000/original-comparison.md),
using the pinned `Devices/MinoltaCS2000` sources from the selected school checkout.
It checks baseline file hashes before accepting comparison results. The tests
execute the original classes against strict simulated serial responses; they
do not substitute copied parsing expressions for the original implementation.

Identical valid instrument payloads should produce exactly the same 401 × N
spectral and 3 × N XYZ arrays. Corrected condition parsing, atomic history,
duration handling, current-buffer reads and manual/strobe behavior have
different expected outcomes, with their reasons in the comparison guide.
Inspect these named outcomes together: a deliberate behavior difference should
not be hidden by removing its test or loosening a numeric tolerance.

## Maintaining the tests

For changes to discovery, command sequences, metadata, timeouts, cleanup,
saved structure or public API:

- Change the corresponding simulator response and observable API assertions;
  add a failure fixture demonstrating the repaired behavior.
- Update the relevant test guide, README and protocol/data reference in the same change
  whenever an operator action or expected result changes.
- Run `colormeasure.runTests` and inspect named results and raw Analyzer output. New
  family tests and MATLAB sources are discovered without maintaining a list.
- Audit old fixtures for outdated reply layouts, final-command assumptions,
  restored defaults, retry expectations, missing metadata and fixed port names.
  Remove obsolete assertions only after identifying the replacement behavior;
  retain useful malformed, incomplete, busy and unsupported-response cases.
- Keep the original baseline hashes pinned. Do not modify the preserved
  original to make a comparison pass. Update the comparison guide's expected
  matches and differences whenever current behavior changes; retain regression
  cases that execute the original failure as well as the repaired path.
- Check examples, saved-field descriptions and source links for staleness.
  Preserve protocol revision distinctions and tests for supported older layouts.
- Keep adapter/view/export fields and `snapshot()` synchronized with native
  persistence, including new metadata and unavailable-value meanings. Update
  demonstration labels, comparison eligibility and both headless/shared-UI
  tests when those contracts change; never infer physical scale from a demo.
- Keep software results and physical-device results separate.
- For metadata changes, keep the parser, simulated replies and field inventory
  consistent about command revision, units, timing and unavailable values.

For another instrument, consult that family's coverage guide and device checklist.

### Runtime compatibility

When changing shared launchers, also exercise the documented
[older-session compatibility check](../session/README.md#troubleshooting-after-an-update)
in a separate synthetic-only process. Check batch and gallery entry points:
a rejected older class must not create a demo folder, acquire a reading or
replace retained readings or registry entries. This does not establish safe
hot-reloading of a live session.

### Original-code test isolation

Supplying `SchoolRoot` selects the original CS-2000 comparisons. A partial or
modified selected baseline fails rather than being silently skipped. Without
`SchoolRoot`, the report identifies original comparisons as not run. Temporary guards
reject real `serialport`, `serialportlist`, legacy `serial` and instrument-object
lookup calls. Original-code comparisons temporarily replace the rejecting
legacy `serial` guard with a simulated class that accepts only its test sentinel
port; every other name is rejected. It implements the original transport calls
without forwarding to any real serial API. The legacy `serial.m` and timing `pause.m` fixtures live under
`tests/original-fixtures/cs2000`, outside every discovered test folder: suite
discovery changes into each folder it scans, and a `pause.m` there makes MATLAB
warn that the name hides a builtin.
Only the corresponding original-code test adds that exact directory, then
restores the prior path. A regression checks `which serialport`, `which serial`
and `which pause` after adding `src` (source installation) without invoking any
of those APIs. No real port enumeration, instrument
connection, acquisition or setting change is part of software validation.
Gonio preflight tests use a recording fake stage and simulated transport; the
runner must not execute physical motion, mounting or network utilities.
